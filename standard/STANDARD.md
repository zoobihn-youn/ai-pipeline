# STANDARD.md — AI 협업 PoC 기준 문서 v1.1 (2026-11-23)

> 모든 PoC가 따르는 공용 기준이다. 각 프로젝트의 PROJECT.md는 맨 위에 이 문서의 버전을 적고, **이 기준과 다른 점만** "기준 예외" 절에 이유와 함께 적는다.
> 근거: ai-pipeline v1에서 실제로 돌려 확인한 규칙만 담았다 (ai-pipeline PROJECT.md 3~19절). 확인 안 된 것은 "안"으로 표시한다.

## 0. 이 문서를 쓰는 법
1. 새 PoC를 시작하거나 기존 PoC에 적용할 때: `NEW-PROJECT-CHECKLIST.md` 순서대로 준비한다.
2. 작업을 시작할 때: 이 문서 → 그 프로젝트의 PROJECT.md → TASK.md 순서로 읽는다. 이전 지시서는 기준으로 쓰지 않는다.
3. 이 문서를 바꿀 때: 버전을 올리고 맨 아래 "변경 기록"에 이유를 적는다. 바꾼 내용은 공용 파이프라인(stage.ps1·n8n)에도 반영한다.

## 1. 역할 분담
| 단계 | 담당 | 하는 일 | 권한 |
|---|---|---|---|
| ① 기획 | 사람 + Claude 채팅 | PROJECT.md·TASK.md 작성, 완료 조건 정의 | — |
| ② 개발 | Claude Code (`claude -p`) | TASK대로 구현, REPORT.md에 주장 기록 | 설정한 폴더와 REPORT.md에만 쓰기, 명령 실행 없음 |
| ③ 코드 리뷰 | Codex (`codex exec`, 읽기 전용) | 실행 **전** 코드 리뷰, 첫 줄 `VERDICT: PASS/BLOCK` | 읽기만 |
| ④ 실행 | 파이프라인 스크립트 (AI 없음) | TASK의 `RUN:` 명령 실행, 종료 코드를 직접 측정 | — |
| ⑤ 1차 검수 | Codex (읽기 전용) | REPORT의 주장과 실제 파일·실행 기록 대조 | 읽기만 |
| ⑥ 2차 검수 | Claude Code 새 세션 (허용 도구 없음) | 지적의 중요도, 놓친 문제, ⑤와의 이견 표, `RECOMMEND: PASS/BLOCK` | 읽기만 |
| ⑦ 판정 | 사람 | RESULT.md를 보고 최종 결정, 병합·push | — |

- 실행 결과는 AI가 보고하지 않고 스크립트가 측정한다. AI가 쓴 종료 코드는 추정이 섞일 수 있다 (v1 확인).

## 2. 검수 독립성
- 개발한 AI와 다른 AI가 리뷰한다 (②Claude ↔ ③·⑤Codex).
- ⑥은 ②와 다른 **새 세션**이다. ③·⑤ 원문을 읽고 그 판단 자체를 검증한다.
- 검수자는 파일을 바꿀 수 없다. 검수자의 출력은 **스크립트가 파일로 기록**한다 (검수자가 기록을 고칠 수 없게).
- 검수자에게 기준 문서(TASK.md, 이번 실행의 REPORT 섹션)는 스크립트가 **표준 입력으로 정확한 글을 넘긴다**. Codex는 Windows 샌드박스에서 셸로 읽은 한글이 깨지기 때문이다 (v1 확인). 코드와 다른 파일은 검수자가 직접 읽는다.

## 3. 문서
| 파일 | 위치 | 쓰는 쪽 | 내용 | Git |
|---|---|---|---|---|
| PROJECT.md | 최상위 | 사람·Claude 채팅 | 프로젝트 기준 규칙, 결정 기록 | 올림 |
| TASK.md | 최상위 | 사람·Claude 채팅 | **이번 작업 하나** | 올림 |
| REPORT.md | 최상위 | ②(주장), ④(측정값, 스크립트) | 맨 위에 추가 | 올림 |
| RESULT.md | 최상위 | 파이프라인 | 단계 요약 + ⑥ 의견, ⑦이 보는 유일한 문서 | 올림 |
| pipeline.json | 최상위 | 사람·Claude 채팅 | 파이프라인 실행 설정 (5절) | 올림 |
| `.pipeline/` | 최상위 | 파이프라인 | STATUS.json, logs/, reviews/ | **안 올림** |

- REPORT.md(개발자의 주장)와 RESULT.md(검수 결론)는 작성자가 달라서 나눈다.
- REPORT.md·RESULT.md는 덮어쓰지 않고 **맨 위에 날짜와 함께 추가**한다. 리뷰 원문은 시도마다 새 파일.
- 파일 인코딩은 UTF-8(BOM 없음). Windows PowerShell 5.1에서 돌리는 스크립트는 ASCII만 쓴다.

## 4. TASK.md 작성 규칙 (품질의 실제 기준)
- 검수 단계가 여러 개여도 **완료 조건이 느슨하면 걸러지지 않는다** (v1: ⑥이 "조건 3은 계획만 있고 확인 결과가 없다"고 지적). 그래서 TASK는 아래를 지킨다.
1. **작업은 하나.** 여러 개면 TASK를 나눈다.
2. **완료 조건은 확인할 수 있게** 쓴다: 명령의 종료 코드, 파일의 존재·내용, 값의 범위처럼 누가 봐도 같은 결과가 나오는 것.
   - 나쁜 예: "잘 동작한다", "보기 좋게", "REPORT에 적는다"(무엇을 확인했는지가 없음)
   - 좋은 예: "`python -m plp regress` 종료 코드 0", "`runs/output.txt` 내용이 정확히 `pipeline ok`"
3. 조건마다 **어느 단계가 확인하는지** 적는다: ③ 코드로 / ④ 실행으로 / ⑤ 결과 대조로. ③은 실행 전이라 실행 결과 조건으로 BLOCK하지 않는다.
4. `RUN:` 한 줄 = ④가 실행할 명령. 여러 단계면 스크립트 하나로 묶는다.
5. **하지 않을 것**을 적는다 (지우면 안 되는 폴더, 바꾸면 안 되는 규칙, 외부 접속 금지 등).
6. **시작 전 확인**: ②가 읽어야 할 문서 목록.
- 양식: `TASK.template.md`

## 5. 실행 설정 (pipeline.json)
- 프로젝트마다 다른 값은 파이프라인 코드가 아니라 프로젝트 최상위 `pipeline.json`에 둔다. 양식: `pipeline.template.json`
- 파일이 없거나 잘못되면 S0에서 멈춘다 (결과 기록 단계는 멈춤 기록을 위해 계속 돈다).
| 키 | 뜻 | 기본값 |
|---|---|---|
| `develop.write_paths` | ②가 쓸 수 있는 경로. **REPORT.md 필수** | 없음 (필수) |
| `develop.model`, `develop.max_turns` | ② 모델·최대 턴 수 | haiku, 10 |
| `second_review.model`, `second_review.max_turns` | ⑥ 모델·최대 턴 수 | haiku, 10 |
| `run.move_before_run` | ④ 실행 전에 내용을 `.pipeline/prev-output/<runId>/`로 옮길 폴더 | 없음 (옮기지 않음) |
| `timeouts_sec.default`, `timeouts_sec.s0`~`s6`·`end` | 단계별 시간 제한(초, 10~7200) | 180 |
| `review.code_paths` | 검수자에게 알려 줄 코드 위치 | 없음 (필수) |
| `review.output_paths` | 검수자에게 알려 줄 실행 결과 위치 | 없음 |
| `ops.run` | 운영 흐름(flow=ops) ④에서 실행할 고정 명령 한 줄. 없으면 운영 흐름은 S0에서 멈춤 | 없음 |
- 경로 규칙: 프로젝트 최상위 기준 상대 경로. `..`·절대 경로·따옴표·cmd 특수 문자(`< > & | ^ %`) 금지 (권한 규칙과 Codex 명령 줄에 그대로 들어가기 때문).
- 주의: `move_before_run`은 그 폴더가 **이번 실행만의 출력**일 때만 쓴다 (image-compare의 `runs/`처럼 누적 데이터 폴더면 넣지 않는다).
- S0이 읽은 설정을 실행 기록에 남긴다 (settings: …).

- 흐름 두 가지 (ai-pipeline PROJECT.md 21절 C): **개발(dev)** = S0→②→③→④(TASK.md `RUN:`)→⑤→⑥→PASS면 `run/<id>` 커밋→⑦ 판정. **운영(ops)** = 코드는 그대로 두고 실행만: S0→④(`ops.run`)→⑤→⑥. S0에서 `review.code_paths` 아래에 바뀐 파일이 있으면 멈추고, ④가 코드를 바꿔도 멈춤. 커밋·⑦ 판정 없음, 보고·결과는 Git에 올리지 않는 `.pipeline/ops/REPORT.md`·`RESULT.md`에 쌓임. n8n "설정" 노드의 `flow` 값(dev/ops)으로 고른다.

## 6. 판정·멈춤 규칙
- ③·⑤ 답의 첫 줄은 정확히 `VERDICT: PASS` 또는 `VERDICT: BLOCK`. 없으면 실패로 멈춤.
- ③ BLOCK → ② 재작업 → ③ 재리뷰. **처음 1회 + 재시도 2회**까지, 그래도 BLOCK이면 멈춤.
- ⑤ BLOCK이어도 ⑥으로 간다 (최종 판단은 ⑥·⑦).
- 멈춤 조건 (모든 단계):
  - Claude: 종료 코드 ≠ 0, `is_error`, `permission_denials` 1건 이상 (결과 본문이 아니라 JSON 필드로 판단)
  - Codex: 종료 코드 ≠ 0, `turn.failed`·`error` 이벤트, 판정 줄 없음
  - 시간 제한 초과 (하위 프로세스까지 종료)
- 멈추면 결과 기록(RESULT.md) 후 n8n 실행을 **실패로 표시**한다.

## 7. Git
- 실행 전부터 바뀌어 있던 파일은 멈추지 않고 **기록만** 한다 (RESULT에 표시).
- 커밋은 **real 전체 실행이 PASS일 때 끝에 한 번**, `run/<runId>` 브랜치에. 멈춘 실행·가짜 실행은 커밋하지 않는다.
- 병합·push는 ⑦ 사람 승인 뒤. 비밀(.env 등)·대용량 결과물·`.pipeline/`은 올리지 않는다.
- 공개 여부는 프로젝트마다 자료를 확인하고 정한다 (PROJECT.md에 기록).

## 8. 사용량
- 새 구조나 새 프로젝트는 **가짜 실행(fake)으로 흐름을 먼저** 확인한 뒤 실제 호출로 바꾼다.
- 일부만 실제(`real:s2,s3` 등)로 돌려 필요한 단계만 확인할 수 있다. 다만 앞 단계가 가짜면 뒤 단계 판단이 달라질 수 있다 (v1: ②가 가짜라 ③이 BLOCK).
- 실행마다 Claude·Codex 호출 수를 기록한다 (RESULT의 AI calls). BLOCK이 나면 재시도만큼 호출이 늘어난다.

## 9. 기록 원칙

- 결정은 날짜와 결정한 사람을 붙여 PROJECT.md에 남긴다.
